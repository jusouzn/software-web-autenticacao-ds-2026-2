## 1.2 Invocação dos servidores e inicialização do ambiente

> **Item de informação IT-1.2** · Autoria: Kesley Soares da Silva · Revisão: Verônica Ribeiro Oliveira Palmeira  
> Referências do item: [[DOCKER, 2026](../referencias.md#ref-docker2026)]; [[POSTGRESQL, 2026](../referencias.md#ref-postgres2026)]; [[ENCODE, 2026](../referencias.md#ref-uvicorn2026)]; [[NGINX, 2026](../referencias.md#ref-nginx2026)]; [[HODGES; JACKSON; BARTH, 2012](../referencias.md#ref-rfc6797)] · Apoio de IA: [[ANTHROPIC, 2026](../referencias.md#ref-anthropic2026)]

Antes de atender qualquer usuário, os servidores precisam ser iniciados e colocados em estado de escuta. No ambiente proposto, a inicialização é feita por um único comando do operador, `docker compose up -d`, que lê o arquivo `docker-compose.yml` do repositório, cria uma rede virtual interna e inicia três contêineres na ordem determinada pelas dependências declaradas [[DOCKER, 2026](../referencias.md#ref-docker2026)]. A Tabela 3 apresenta a sequência e o estado resultante de cada passo.

**Tabela 3 – Sequência de inicialização do ambiente e resultados**

| Ordem | Contêiner | Comando invocado | Processamento | Estado resultante |
|---|---|---|---|---|
| 1 | `db` | `postgres` (imagem `postgres:16`) | Na primeira execução, cria o *cluster* de dados e executa os scripts de `/docker-entrypoint-initdb.d/` (criação da tabela `usuario` e carga de usuários de teste) | Processo *postmaster* escutando na porta 5432 da rede interna; verificação de saúde `pg_isready` retorna sucesso |
| 2 | `app` | `uvicorn app.principal:app --host 0.0.0.0 --port 8000 --workers 2` | Uvicorn importa o módulo `app.principal`, obtém o objeto `app` (FastAPI), lê variáveis de ambiente (`DATABASE_URL`, parâmetros Argon2id) e cria dois processos trabalhadores | Porta 8000 em escuta na rede interna; *pool* de conexões com o banco criado; mensagem `Application startup complete` no log |
| 3 | `web` | `nginx -g 'daemon off;'` | Processo mestre lê `/etc/nginx/nginx.conf`, valida a configuração, carrega certificado e chave TLS, abre as portas 80 e 443 e cria processos trabalhadores | Portas 80 e 443 publicadas no host; único ponto de entrada externo |

*Fonte: elaborada pelos autores (2026), com base em [[DOCKER, 2026](../referencias.md#ref-docker2026)], [[POSTGRESQL, 2026](../referencias.md#ref-postgres2026)], [[ENCODE, 2026](../referencias.md#ref-uvicorn2026)] e [[NGINX, 2026](../referencias.md#ref-nginx2026)].*

Somente o contêiner `web` publica portas para fora do host. O servidor de aplicação e o banco de dados são acessíveis apenas pela rede interna do Docker, o que reduz a superfície de ataque. A configuração do Nginx que materializa esse papel é resumida a seguir; os blocos correspondem às responsabilidades da Tabela 2.

```nginx
limit_req_zone $binary_remote_addr zone=autenticacao:10m rate=5r/m;

server {                                  # porta 80: apenas redireciona
    listen 80;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    http2 on;
    ssl_certificate     /etc/nginx/certs/servidor.crt;
    ssl_certificate_key /etc/nginx/certs/servidor.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Content-Security-Policy "default-src 'self'" always;

    location / {                          # conteúdo estático
        root /usr/share/nginx/html;
        index login.html;
    }
    location /api/ {                      # conteúdo dinâmico
        limit_req zone=autenticacao burst=5 nodelay;
        limit_req_status 429;
        proxy_pass http://app:8000;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        error_page 429 = @limite_excedido;
    }
    location @limite_excedido {           # 429 no mesmo formato da API
        default_type application/problem+json;
        add_header Retry-After 60 always;
        return 429 '{"type":"about:blank","title":"Limite de tentativas","status":429,"detail":"Muitas tentativas. Tente novamente mais tarde."}';
    }
}
```

O primeiro bloco `server` redireciona qualquer acesso HTTP sem criptografia para HTTPS; o cabeçalho `Strict-Transport-Security` instrui o navegador a usar apenas HTTPS nas visitas seguintes [[HODGES; JACKSON; BARTH, 2012](../referencias.md#ref-rfc6797)]. O bloco `location /` faz o Nginx atuar como servidor de arquivos, e o bloco `location /api/` faz o Nginx atuar como proxy reverso, repassando a requisição ao serviço `app` resolvido pelo DNS interno do Docker [[NGINX, 2026](../referencias.md#ref-nginx2026); [DOCKER, 2026](../referencias.md#ref-docker2026)]. Para implantação local de desenvolvimento, o certificado pode ser autoassinado; em produção, deve ser emitido por autoridade certificadora reconhecida.
