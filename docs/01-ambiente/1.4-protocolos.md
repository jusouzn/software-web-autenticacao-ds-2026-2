## 1.4 Protocolos e formatos utilizados

> **Item de informação IT-1.4** · Autoria: Kesley Soares da Silva · Revisão: Júlia de Souza Nascimento  
> Referências do item: [[TANENBAUM; FEAMSTER; WETHERALL, 2021](../referencias.md#ref-tanenbaum2021)]; [[MOCKAPETRIS, 1987](../referencias.md#ref-mockapetris1987)]; [[EDDY, 2022](../referencias.md#ref-rfc9293)]; [[RESCORLA, 2018](../referencias.md#ref-rfc8446)]; [[FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)]; [[FIELDING; NOTTINGHAM; RESCHKE, 2022b](../referencias.md#ref-rfc9112)]; [[THOMSON; BENFIELD, 2022](../referencias.md#ref-rfc9113)]; [[ASGI, 2026](../referencias.md#ref-asgi2026)]; [[WHATWG, 2026b](../referencias.md#ref-whatwghtml2026)]; [[BRAY, 2017](../referencias.md#ref-rfc8259)]; [[NOTTINGHAM; WILDE; DALAL, 2023](../referencias.md#ref-rfc9457)]; [[POSTGRESQL, 2026](../referencias.md#ref-postgres2026)] · Apoio de IA: [[ANTHROPIC, 2026](../referencias.md#ref-anthropic2026)]

A Tabela 5 consolida, por camada, os protocolos e formatos que os softwares da [Seção 1.1](1.1-componentes.md#11-visão-geral-e-componentes-do-ambiente) utilizam para se comunicar. A organização em camadas permite que cada software trate apenas da sua responsabilidade: o navegador e o Nginx não conhecem a estrutura da tabela de usuários, e a aplicação não conhece detalhes de TCP ou TLS [[TANENBAUM; FEAMSTER; WETHERALL, 2021](../referencias.md#ref-tanenbaum2021)].

**Tabela 5 – Protocolos e formatos por camada**

| Camada | Protocolo ou formato | Onde é usado | Referência |
|---|---|---|---|
| Aplicação (nomes) | DNS | Navegador ↔ servidor DNS; resolução de `app` e `db` na rede Docker | [[MOCKAPETRIS, 1987](../referencias.md#ref-mockapetris1987)] |
| Transporte | TCP | Todas as conexões (443, 8000, 5432) | [[EDDY, 2022](../referencias.md#ref-rfc9293)] |
| Segurança | TLS 1.3 (1.2 aceito) | Navegador ↔ Nginx | [[RESCORLA, 2018](../referencias.md#ref-rfc8446)] |
| Aplicação (Web) | HTTP/1.1 e HTTP/2 | Navegador ↔ Nginx (HTTP/2 ou HTTP/1.1); Nginx ↔ Uvicorn (HTTP/1.1) | [[FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)], [[FIELDING; NOTTINGHAM; RESCHKE, 2022b](../referencias.md#ref-rfc9112)], [[THOMSON; BENFIELD, 2022](../referencias.md#ref-rfc9113)] |
| Interface servidor-aplicação | ASGI 3.0 | Uvicorn ↔ FastAPI (chamada em processo) | [[ASGI, 2026](../referencias.md#ref-asgi2026)] |
| Dados (Web) | HTML, CSS, JavaScript | Página de login | [[WHATWG, 2026b](../referencias.md#ref-whatwghtml2026)] |
| Dados (API) | JSON; *Problem Details* (`application/problem+json`) | Corpo das requisições e respostas da API | [[BRAY, 2017](../referencias.md#ref-rfc8259)], [[NOTTINGHAM; WILDE; DALAL, 2023](../referencias.md#ref-rfc9457)] |
| Banco de dados | Protocolo de mensagens do PostgreSQL; SQL | Aplicação ↔ PostgreSQL | [[POSTGRESQL, 2026](../referencias.md#ref-postgres2026)] |

*Fonte: elaborada pelos autores (2026).*

Os códigos de status HTTP têm papel central no projeto, porque são o meio padronizado de o servidor comunicar ao cliente o resultado do processamento. Conforme [[FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)], a classe 2xx indica sucesso, a classe 4xx indica erro atribuível ao cliente e a classe 5xx indica erro do servidor. A aplicação utiliza `200 OK` para autenticação bem-sucedida e `401 Unauthorized` para credenciais inválidas; os demais códigos e seus significados estão definidos no contrato da API, na [Seção 2.5](../02-projeto/2.5-api.md#25-contrato-da-api).
