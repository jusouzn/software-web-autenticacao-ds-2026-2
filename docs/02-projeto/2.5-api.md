## 2.5 Contrato da API

> **Item de informação IT-2.5** · Autoria: Verônica Ribeiro Oliveira Palmeira · Revisão: Júlia de Souza Nascimento

A API expõe um único recurso. O contrato abaixo é a referência para a implementação do servidor ([Seção 2.3.1](2.3-componentes.md#231-componentes-da-camada-de-interface-api)) e do cliente ([Seção 2.3.4](2.3-componentes.md#234-componentes-da-camada-de-apresentação)); o FastAPI publica o mesmo contrato em formato OpenAPI no caminho `/api/docs`, apenas em ambiente de desenvolvimento [[RAMÍREZ, 2026](../referencias.md#ref-fastapi2026)].

**Requisição.** `POST /api/v1/autenticacao`, com cabeçalho `Content-Type: application/json` e corpo JSON [[BRAY, 2017](../referencias.md#ref-rfc8259)]:

```json
{ "identificador": "julia@exemplo.com.br", "senha": "S3nh@-de-teste" }
```

O método `POST` foi escolhido porque as credenciais seguem no corpo da mensagem, e não na URL, que costuma ser registrada em logs e no histórico do navegador. O prefixo `v1` permite evoluir o contrato sem quebrar clientes existentes.

**Resposta de sucesso.** `200 OK`, `Content-Type: application/json`, `Cache-Control: no-store`:

```json
{
  "autenticado": true,
  "usuario": {
    "id": "6f1c2a9e-4b7d-4c3e-9a51-2f0d8e7b1c44",
    "login": "julia",
    "email": "julia@exemplo.com.br",
    "nome": "Júlia de Souza Nascimento"
  }
}
```

**Resposta de falha de autenticação.** `401 Unauthorized`, `Content-Type: application/problem+json`, no formato *Problem Details* [[NOTTINGHAM; WILDE; DALAL, 2023](../referencias.md#ref-rfc9457)]. A resposta é idêntica para usuário inexistente e para senha incorreta (RN04):

```json
{
  "type": "about:blank",
  "title": "Falha de autenticação",
  "status": 401,
  "detail": "Login, e-mail ou senha inválidos."
}
```

A especificação de HTTP exige que respostas `401` incluam o cabeçalho `WWW-Authenticate` com um desafio [[FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)]. Como a autenticação é feita por formulário, e não por um esquema HTTP padronizado como `Basic`, a resposta inclui `WWW-Authenticate: Formulario realm="autenticacao"`. O esquema não é reconhecido pelos navegadores, o que evita a abertura da janela nativa de login, e ainda assim cumpre o requisito do protocolo.

A Tabela 13 lista todas as respostas possíveis.

**Tabela 13 – Códigos de status da API**

| Código | Situação | Quem gera | `detail` |
|---|---|---|---|
| `200 OK` | Credenciais válidas | Aplicação | (corpo de sucesso) |
| `400 Bad Request` | JSON malformado, campo ausente, campo extra ou tamanho fora dos limites definidos na [RN03](2.1-requisitos.md#21-escopo-e-requisitos) | Aplicação (`TratadorErros`) | "Requisição inválida: informe identificador e senha." |
| `401 Unauthorized` | Usuário inexistente ou senha incorreta | Aplicação (`TratadorErros`) | "Login, e-mail ou senha inválidos." |
| `405 Method Not Allowed` | Método diferente de `POST` | Aplicação (FastAPI) | — (cabeçalho `Allow: POST`) |
| `415 Unsupported Media Type` | `Content-Type` diferente de `application/json` | Aplicação (`TratadorErros`) | "Envie o corpo em JSON." |
| `429 Too Many Requests` | Limite de taxa excedido (RNF03) | Nginx | "Muitas tentativas. Tente novamente mais tarde." |
| `500 Internal Server Error` | Erro inesperado | Aplicação (`TratadorErros`) | "Erro interno." |
| `503 Service Unavailable` | Banco de dados indisponível | Aplicação (`TratadorErros`) | "Serviço temporariamente indisponível." |

*Fonte: elaborada pelos autores (2026), com base em [[FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)] e [[NOTTINGHAM; FIELDING, 2012](../referencias.md#ref-rfc6585)].*

O código `400` foi preferido ao `422 Unprocessable Content`, padrão do FastAPI para erros de validação, para que o cliente trate de forma única qualquer requisição mal formada; o `TratadorErros` substitui o comportamento padrão. As respostas `429` e `503` incluem o cabeçalho `Retry-After` [[NOTTINGHAM; FIELDING, 2012](../referencias.md#ref-rfc6585); [FIELDING; NOTTINGHAM; RESCHKE, 2022a](../referencias.md#ref-rfc9110)].

Para garantir o comportamento descrito, o Nginx deve ser configurado com `limit_req_status 429` e com o tratamento correspondente para incluir o cabeçalho `Retry-After` na resposta de limite de taxa.
