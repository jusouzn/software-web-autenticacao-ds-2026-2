## 2.1 Escopo e requisitos

> **Item de informação IT-2.1** · Autoria: Júlia de Souza Nascimento · Revisão: Verônica Ribeiro Oliveira Palmeira

O escopo é o definido no enunciado da APS: **somente verificação de credenciais**. A Tabela 6 apresenta os requisitos funcionais, derivados diretamente das quatro etapas do domínio (entrada, validação, comparação e decisão) e das duas formas de retorno. A redação segue a recomendação de requisitos verificáveis e não ambíguos de [SOMMERVILLE, 2016].

**Tabela 6 – Requisitos funcionais**

| ID | Requisito | Origem no enunciado |
|---|---|---|
| RF01 | O sistema deve receber credenciais compostas por um identificador (login ou e-mail) e uma senha, enviadas pelo cliente. | Entrada de credenciais |
| RF02 | O sistema deve verificar se existe, no repositório de dados, um usuário com o identificador informado. | Validação das credenciais |
| RF03 | O sistema deve comparar a senha informada com a credencial registrada para o usuário. | Comparação da credencial |
| RF04 | O sistema deve decidir entre "autenticado" (credenciais válidas) e "não autenticado" (credenciais inválidas ou usuário inexistente). | Decisão de autenticação |
| RF05 | Em caso de sucesso, o sistema deve retornar um objeto com a identificação do usuário (identificador único, login, e-mail e nome). | Retorno em caso de sucesso |
| RF06 | Em caso de falha, o sistema deve retornar um erro de autenticação. | Retorno em caso de falha |

*Fonte: elaborada pelos autores (2026), a partir do Apêndice A do enunciado da APS.*

As regras de negócio da Tabela 7 refinam os requisitos funcionais em pontos que o enunciado deixa em aberto.

**Tabela 7 – Regras de negócio**

| ID | Regra |
|---|---|
| RN01 | Se o identificador contiver o caractere `@`, é tratado como e-mail; caso contrário, como login. |
| RN02 | Antes da busca, o identificador é normalizado: remoção de espaços nas extremidades e conversão para minúsculas. A senha não é normalizada. |
| RN03 | O identificador deve ter de 1 a 254 caracteres e a senha, de 1 a 128 caracteres; fora desses limites, a requisição é rejeitada como inválida (não como falha de autenticação). |
| RN04 | Usuário inexistente e senha incorreta produzem exatamente a mesma resposta de erro, para não revelar quais identificadores existem [OWASP, 2026a]. |
| RN05 | O objeto de identidade retornado nunca contém a senha nem o *hash* da senha. |

*Fonte: elaborada pelos autores (2026).*

Os requisitos não funcionais da Tabela 8 foram classificados segundo as características do modelo de qualidade de produto da [ISO/IEC, 2023].

**Tabela 8 – Requisitos não funcionais**

| ID | Característica (ISO/IEC 25010) | Requisito |
|---|---|---|
| RNF01 | Segurança – confidencialidade | As credenciais trafegam apenas por HTTPS (TLS 1.2 ou superior); acessos HTTP são redirecionados. |
| RNF02 | Segurança – confidencialidade | Senhas são armazenadas somente como *hash* Argon2id com sal individual. |
| RNF03 | Segurança – resistência | Tentativas de autenticação são limitadas a 5 por minuto por endereço IP, com rajada de 5. |
| RNF04 | Segurança – confidencialidade | Respostas de sucesso e de falha têm tempo de processamento equivalente, existindo ou não o usuário. |
| RNF05 | Eficiência de desempenho | O tempo de resposta do servidor para uma autenticação deve ser inferior a 500 ms no percentil 95, em carga de 10 requisições simultâneas. |
| RNF06 | Compatibilidade – interoperabilidade | A API usa JSON e códigos de status HTTP padronizados, permitindo uso por qualquer cliente HTTP. |
| RNF07 | Manutenibilidade – modularidade | O serviço de autenticação não depende diretamente do banco de dados nem do algoritmo de *hash*, mas de interfaces substituíveis. |
| RNF08 | Flexibilidade – instalabilidade | O ambiente completo é iniciado com um único comando (`docker compose up -d`). |

*Fonte: elaborada pelos autores (2026), com base em [ISO/IEC, 2023].*

**Fora do escopo.** Cadastro, alteração e recuperação de senha; emissão de *token* ou cookie de sessão; autorização (perfis e permissões); autenticação multifator; bloqueio de conta. Os usuários do repositório são carregados por um script de carga inicial, usado apenas para teste, que não faz parte do software projetado. O objeto de identidade retornado (RF05) é o insumo para que o cliente, ou outro sistema, continue o fluxo com o usuário autenticado.
